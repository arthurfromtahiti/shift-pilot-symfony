# Relecture — WORKFLOW_LIVRAISONS_EN_ATTENTE.md

## Verdict global
À corriger — la lecture du code est globalement bonne, mais l'objectif contient une extrapolation métier non prouvée alors que le document affirme que toutes ses affirmations sont `VÉRIFIÉ_CODE`. Le filtre exact visible dans le code est `status !== 'livre'`, pas la notion métier de « plan de charge actif ».

## Problèmes bloquants
- Le paragraphe **Objectif** invente une sémantique métier plus forte que la preuve disponible : « Ce sous-ensemble représente le "plan de charge" actif » n'est soutenu ni par [src/Controller/DeliveryController.php](/paperclip/instances/default/projects/be2f6065-a710-4a1d-8bb7-531efdbc6f23/4e3d3e53-3858-4d53-b8fd-df0d579cb6ed/shift-pilot-symfony/src/Controller/DeliveryController.php:25), ni par [README.md](/paperclip/instances/default/projects/be2f6065-a710-4a1d-8bb7-531efdbc6f23/4e3d3e53-3858-4d53-b8fd-df0d579cb6ed/shift-pilot-symfony/README.md:1), ni par les tests dans [tests/DeliveryControllerTest.php](/paperclip/instances/default/projects/be2f6065-a710-4a1d-8bb7-531efdbc6f23/4e3d3e53-3858-4d53-b8fd-df0d579cb6ed/shift-pilot-symfony/tests/DeliveryControllerTest.php:16). Le code ne prouve qu'une inclusion de toute livraison dont `status` est différent de `'livre'`, ce que le document reconnaît d'ailleurs lui-même dans la règle « Toute valeur de statut autre que 'livre' est incluse ».
- La phrase « n'ont pas encore atteint leur destination » est trop catégorique au regard de la règle observée. Avec la logique réelle `fn(array $d) => $d['status'] !== 'livre'` dans [src/Controller/DeliveryController.php](/paperclip/instances/default/projects/be2f6065-a710-4a1d-8bb7-531efdbc6f23/4e3d3e53-3858-4d53-b8fd-df0d579cb6ed/shift-pilot-symfony/src/Controller/DeliveryController.php:30), un futur statut `annule` ou `retarde` serait aussi retourné sans prouver que la livraison est « en cours d'acheminement ». Présenter cette interprétation comme un fait contredit le niveau de preuve annoncé.

## Problèmes mineurs
- La question ouverte parle de « routage `annotation` » dans [WORKFLOW_LIVRAISONS_EN_ATTENTE.md](/paperclip/instances/default/projects/be2f6065-a710-4a1d-8bb7-531efdbc6f23/4e3d3e53-3858-4d53-b8fd-df0d579cb6ed/shift-pilot-symfony/.onboarding/workflows/WORKFLOW_LIVRAISONS_EN_ATTENTE.md:34), alors que le contrôleur utilise des attributs PHP `#[Route(...)]` dans [src/Controller/DeliveryController.php](/paperclip/instances/default/projects/be2f6065-a710-4a1d-8bb7-531efdbc6f23/4e3d3e53-3858-4d53-b8fd-df0d579cb6ed/shift-pilot-symfony/src/Controller/DeliveryController.php:25). `config/routes.yaml` déclare bien `type: annotation`, donc ce n'est pas un faux fonctionnel, mais la formulation mélange deux niveaux et gagnerait à être précisée.

## Recommandations de correction
- Réécrire l'**Objectif** en restant au niveau de preuve du code : « retourner les livraisons dont `status` est différent de `livre` » est prouvé ; « plan de charge actif » et « n'ont pas encore atteint leur destination » ne le sont pas.
- Conserver l'analyse actuelle sur l'ouverture du filtre aux futurs statuts, car c'est précisément l'élément de preuve qui montre pourquoi l'interprétation métier actuelle est trop forte.
- Harmoniser la formulation sur le routage pour parler soit d'attributs PHP, soit du chargement de routes par Symfony, sans les confondre.
